# フェーズ1'(改訂条件案)の実装メモ

Notion「🔧 改良版ファネル並行運用計画」で方向性合意済みのフェーズ1'条件を、実際にEDINET DBでスクリーニングし、`candidates_phase1prime_YYYYMMDD.csv` として出力する手順。

## 条件の対応

| 項目 | 現行フェーズ1 | フェーズ1'(改訂案) | 実装状況 |
|---|---|---|---|
| 東証グロース市場 | 必須 | 必須(変更なし) | 自動判定 |
| 売上高YoY | +10%以上 | 0%以上に緩和 | 自動判定 |
| 利益条件 | YoY+20%以上のみ | YoY+20%以上 **または** 黒字転換 **または** 赤字幅縮小 | **YoY+20%以上の部分のみ自動判定**。黒字転換・赤字縮小の判定は未実装(下記「未実装部分」参照) |
| ROE | 10%以上必須 | フィルタから撤廃(参考記録のみ) | 自動判定(フィルタ外し、値は記録) |

## EDINET DBスクリーニング条件(実装済み部分)

`screen_companies` (EDINET DB MCP) を以下の条件で実行:

```json
{
  "conditions": [
    {"metric": "revenue-growth", "operator": "gte", "value": 0},
    {"metric": "ni-growth", "operator": "gte", "value": 20},
    {"metric": "roe", "operator": "gte", "value": -100000}
  ],
  "market": "growth"
}
```

(ROE条件は実質フィルタなし。値を表示させるためだけに極端に緩い閾値を指定している)

得られた各社について、以下で分類:

- `revenue_growth >= 10` かつ `ni_growth >= 20` かつ `roe >= 10` → **フェーズ1(現行)**
- 上記以外(= `revenue_growth` が0〜10%未満、または `roe` が10%未満) → **フェーズ1'のみ(自動判定)**

## 2026-09-15実行結果

- フェーズ1(現行)該当: 118件
- フェーズ1'のみ(自動判定で新たに追加): 67件
- 合計: 185件

→ `candidates_phase1prime_20260915.csv` に出力済み。列: `code, name, industry, revenue_growth_pct, ni_growth_pct, roe_pct, 候補ルール`

このファイルをそのまま(または既存の`candidates.csv`と差し替えて)`jquants_screening.py`に渡すと、52週新高値の実績判定結果(`new_highs_*.csv`)に「候補ルール」列が引き継がれる(`jquants_screening.py`は`候補ルール`列があれば自動でパススルーするよう対応済み)。

## 未実装部分: 黒字転換・赤字幅縮小の判定

フェーズ1'の利益条件のうち「黒字転換」「赤字幅縮小」は、今回は自動判定に含めていない。理由:

1. 運用計画書(Notion)自体に「赤字縮小の定量基準は未確定」と明記されており、閾値を私の判断で決め打ちするのは適切でないため。
2. `ni-growth`(前年比%)は前年が赤字の場合に符号が反転して意味を持たなくなる(例: 前年-100→今年+50でも計算上-150%と出る)。正しく判定するには、各社の「前年の純利益が実際にマイナスだったか」を個別に(`get_financials`等で)確認する必要があり、対象社数(revenue>=0かつni_growth<20の約247社)を考えると、既存の「業績の質」チェック(Week 2の手動ステップ)と同様、機械的な一括判定ではなく個別確認が現実的。

対応案(次回検討): 疑似売買まで進んだ銘柄など、母数が絞られた段階で個別に`get_financials`を確認し、黒字転換/赤字縮小に該当するかを手動判定する運用(業績の質チェックと同じ位置づけ)。

## フェーズ2'(実装済み: 2026-09-15)

`jquants_phase2prime.py` を新規作成。`jquants_screening.py` が出力する `new_highs_*.csv`(実際に52週新高値を更新したイベント一覧)を入力に取り、各イベントについて新高値更新日+5営業日後の株価データをJ-Quants APIから取得し、以下を判定する:

- 乖離率(+5営業日後終値 vs 新高値更新日の高値)が+10%以上 → `GO(乖離率条件クリア)`。これが主判定。
- 出来高倍率(新高値更新日の出来高 ÷ 直前20営業日平均)が3倍以上 → 参考シグナルとして記録するのみ(単独では判定に使わない)。
- 移動平均線整合性は不採用(バックテストで判別力なしと確認済みのため、計算自体を行わない)。

+5営業日分のデータがまだ存在しない(新高値更新から日が浅い)イベントは `判定待ち(+5営業日未到達)` として出力され、確定判定済みの行だけが次回実行時にスキップされる(=日を置いて再実行すれば、判定可能になった分だけ自動的に埋まっていく)。

実行方法・出力形式はスクリプト冒頭のdocstringを参照。出力: `phase2prime_results_YYYYMMDD.csv`(code, name, 候補ルール, entry_date, entry_high, volume_ratio, deviation_pct, phase2_signal, volume_note)。

運用上の注意: このスクリプトも実際のJ-Quants APIへのネットワーク接続が必要なため、`jquants_screening.py`と同様にMacの本物のTerminal.appで実行する。まだ実運用では未実行(候補銘柄185件について、52週新高値更新の実績が確定してから初めて意味を持つため、`jquants_screening.py`の実行が前提)。
